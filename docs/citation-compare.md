# Citation import: differential comparison with ProseCraft

The citation importers (`crates/core/src/citations/{import,bibtex,ris}.rs` and
`crates/core/src/csl.rs`) are compared with ProseCraft's own `importCitations(text, filename)`
on a large generated corpus. The whole result is compared as JSON text: the format, every item and
every warning. This file records how to run it, what the last run found, and an evaluation of
third-party crates that could replace the hand-written parsers.

## Running it

The corpus is generated by ProseCraft's TypeScript, so the generator lives in a ProseCraft
checkout: `src/citation-compare.gen.test.ts` on the `tools/rust-fixtures` branch of the fork (the
same branch as the fixture generator, see `crates/core/tests/fixtures/README.md`). It is seeded and
deterministic. The corpus (about 100 MB) is not committed.

```sh
# In a ProseCraft checkout of tools/rust-fixtures (npm install, then npx svelte-kit sync once):
PROSECRAFT_CITATION_CORPUS=/tmp/citation-corpus.json \
PROSECRAFT_CITATION_SEED=20261118 PROSECRAFT_CITATION_SCALE=1 \
  npx vitest run src/citation-compare.gen.test.ts

# In this repository:
PROSECRAFT_CITATION_CORPUS=/tmp/citation-corpus.json \
  cargo test -p prosecraft-core --test citation_compare -- --ignored --nocapture
```

The Rust test (`crates/core/tests/citation_compare.rs`) prints a table per category and writes
every difference, panic and slow case (over 2 s) to `<corpus>.report.json`, shortest input first.
It fails if any case outside the report-only buckets below differs.

To check a hand-shrunk input against both sides, write `[{ "text": …, "filename": … }]` to a file
and run either side in replay mode with `PROSECRAFT_CITATION_REPLAY=in.json,out.json` (the
vitest file, or `cargo test … --test citation_compare citation_import_replay -- --ignored`).

`meta` in the corpus records the generator commit, seed, scale, Node version (V8's `JSON.parse`
messages depend on it) and the sha256 of the cases. The same seed, scale and commit give a
byte-identical file.

## Results

Run on 2026-11-18 against ProseCraft upstream `2d1cf18` (its citation code is unchanged since
`7dae544`, the commit the port follows), generator commit `46ea299`, Node v26.2.0.

**Before the fixes in this change**, on the first 42,305-input corpus (the same seed, before the
`realistic` categories were added), 1,870 inputs differed:

| Cause | Inputs | Fix |
|---|---:|---|
| The field-name and `@string` key check `/^[a-z0-9_.-]+$/i`: under `i`, `regress` matches `ſ` (long s, which lower-casing leaves alone) as `s`; JavaScript without `u` never folds a non-ASCII character onto ASCII. ProseCraft warns `Invalid @string macro key "ſ" skipped.` and keeps the bare token; the port defined the macro | 1,493 | `bibtex.rs`: the rule is spelled `[A-Za-z0-9_.-]` without `i` |
| A lone surrogate written as a JSON escape (`"\ud83d"`) in a CSL-JSON string: ProseCraft keeps it, the port turned it into U+FFFD (and the fallback id's fingerprint changed with it) | 339 | `csl.rs`: `cleanSingleLine`/`cleanMultiLine` work on UTF-16 units |
| `JSON.parse` on an escape of a character past U+00FF (`"\İ"`): V8 reports `Unexpected token 'İ', …` rather than `Bad escaped character` | 1 | `js/parse_message.rs` |
| Warning text holding half a surrogate pair (see below) | 37 | none (report-only) |

The three fixed cases are added to `citations-import.json` (the fixture test fails without the
fixes).

**After the fixes: 0 of 48,305 inputs differ.** A second seed (7, 42,305 inputs) also gives 0.
The run takes about 3.5 s; the slowest input (the 5,000-item BibTeX file) 42 ms. No panics.

Report-only buckets, counted but not failing the run:

- **`lossy-warning` (35 inputs):** a CSL-JSON syntax error at an astral character. V8 names the
  UTF-16 unit it stopped at (`Unexpected token '\ud83d'`) and cuts its excerpt by units, so the
  warning holds half a surrogate pair. Our warnings are `String`s, which cannot, so they hold U+FFFD
  there. Both display the same text, and warnings are not stored.
- **`js-prototype` (300 inputs):** entry types, bare tokens and months that are exactly
  `constructor` or `__proto__` (any case, also `CONSTRUCTOR.`). ProseCraft finds
  `Object.prototype` members in its lookup tables for them. The port follows the fix in upstream PR
  jennraeross/ProseCraft#48 instead: against a corpus generated from the fork's
  `tools/rust-fixtures-upstream-fixes` (that fix merged in), all 300 match, and all 48,305 inputs
  match overall (2026-11-18). Against a corpus from unfixed ProseCraft, 139 of the 300 differ.

Not checked here: other JavaScript engines' `JSON.parse` messages (WebKit words them differently;
ProseCraft shows those on macOS and Linux) and lone surrogates in the input text itself, which a
Rust `&str` cannot hold.

## Third-party crates

Could a crate replace the hand-written BibTeX and RIS parsing? The candidates were run over the
same corpus with `tools/citation-crate-eval` (a standalone crate, outside the workspace, so the
candidates never enter `Cargo.lock`):

```sh
cd tools/citation-crate-eval
cargo run --release -- /tmp/citation-corpus.json /tmp/crate-eval.json
```

Two routes per crate:

- **tokenizer:** the crate reads the file (entries, fields, macros, concatenation); its values
  are written back as plain BibTeX and handed to our importer, so the LaTeX, names, dates and CSL
  mapping stay ours. A value plain BibTeX cannot carry counts as a **bridge** failure.
- **full:** the crate's own model (its LaTeX decoding, names, dates, types) mapped onto
  ProseCraft's CSL fields, then checked by our `normalize_csl_items_detailed`.

`craft-libs` has nothing for BibTeX, RIS or CSL-JSON today. Its open issue storytold/craft-libs#2103
asks where such readers should live once WordCraft's (wordcraft#1217, reading into
`craft_wordmodel::Source`, not CSL) merge.

On ProseCraft's own import test inputs (the Zotero export and others in `citations-import.json`,
18 BibTeX and 8 RIS files): biblatex tokenizer 12 of 18 identical (2 rejected), biblatex full 10,
serde_bibtex 12, nom-bibtex 10, biblib 0 of 18 BibTeX and 2 of 8 RIS.

"Stack overflow" is a self-referencing macro (`@string{a = a # "x"}`): `biblatex::Bibliography` and
`nom-bibtex` expand it without bound and abort the process (two runs confirmed it; the harness
detects the cycle beforehand to keep running). `nom-bibtex` also panics on 46 malformed files.
No crate produces ProseCraft's warnings (offsets, the field that was skipped), so a replaced parser
would always differ there.

(a) the crate is more correct, (b) ProseCraft is more correct, (c) cosmetic or equivalent.

| Kind | Crates | Example | ProseCraft | Crate | Class |

### Recommendation: keep ours

- On realistic exports a crate is usable only as a **tokenizer** (biblatex, nom-bibtex and
  serde_bibtex: 3,000 of 3,000 identical). Their full models differ on half (biblatex) or all
  (biblib) of the same files, mostly in ways where ProseCraft is right.
- Off the happy path every BibTeX crate rejects the **whole file** for a single problem
  (biblatex: 54 % of generated and 75 % of malformed inputs, against ProseCraft's per-entry
  recovery), two of them crash on a self-referencing macro, and none produces ProseCraft's
  warnings. Using one as the tokenizer would mean keeping our parser as the fallback, so it saves
  no code and adds a dependency.
- For RIS the only candidate, biblib, exposes just a normalised model that swaps `First Last`
  names and merges editors; 84 % of realistic RIS files differ.
- The port matches ProseCraft on all 48,305 inputs after this change, runs the whole corpus in
  3.5 s, and has no panics. The parsing code (`bibtex.rs`, `ris.rs`, `import.rs`) is about 1,400 lines.

If a shared reader is wanted later, the better route is craft-libs (#2103): a reader with
per-entry recovery, built from this port, rather than an outside crate. `biblatex`'s
`RawBibliography` would be the tokenizer to look at again if it gains error recovery.
